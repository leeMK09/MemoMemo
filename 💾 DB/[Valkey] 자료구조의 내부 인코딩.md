# 자료구조의 내부 인코딩

- Valkey에서 같은 명령어를 쓰는데도 메모리 사용량이 5~10배 차이 나는 경우가 있다
- 이유는 Valkey 의 모든 컬렉션 타입(`Hash`, `List`, `Set`, `Sorted Set`)이 2~3개의 서로 다른 내부 저장 방식을 가지고 있기 때문이다
- 이 저장 방식을 인코딩(encoding)이라 부르고, 어떤 걸 사용할지는 서버가 데이터 크기를 보고 알아서 결정한다
- 문제는 명령어 인터페이스가 동일해서 애플리케이션 코드만 봐서는 지금 어떤 인코딩인지 알 수 없다는 점이다
    - 확인하려면 `OBJECT ENCODING <key>` 명령어를 사용해야 한다
    - 메모리는 `MEMORY USAGE <key>` 로 알 수 있다

**타입별 인코딩 목록**

- `String` : `int` -> `embstr` -> `raw`
- `Hash` : `listpack` -> `hashtable`
- `List` : `listpack` -> `quicklist`
- `Set` : `intset` 또는 `listpack` -> `hashtable`
- `Sorted Set` : `listpack` -> `skiplist` (Valkey 9.2 부터 `btree`)
- 왼쪽이 작을 때 쓰는 인코딩, 오른쪽이 커졌을 때 쓰는 인코딩이다

</br>

## listpack - 작을 때 쓰는 공통 인코딩

- `listpack`은 길이 접두사가 붙은 하나의 연속된 바이트 배열이다
    - `[총길이][엔트리수][len]field1[len]value1[len]field2...`
- 포인터가 전혀 없다
- 특정 필드를 찾으려면 앞에서부터 쭉 훑어야 한다
    - 조회가 O(N)이다
- 그런데 데이터가 작을 때는 이게 오히려 더 빠르다
    - 메모리가 한 덩어리로 연속되어 있어서 CPU 가 한 번에 캐시로 끌어올린다
    - 여기서 말하는 캐시는 CPU 안에 있는 작고 아주 빠른 메모리(L1/L2)를 말한다
        - DRAM(일반 메모리) 접근은 L1 캐시보다 약 50배 빠르다
    - 즉 포인터를 따라다니며 50배 느린 메모리 접근을 여러 번 하는 것보다, 연속된 128개를 그냥 훑는 게 더 빠르다
- 반대로 `hashtable`은 진짜 해시 테이블이라 조회가 O(1)이지만 엔트리마다 포인터와 메타데이터 오버헤드를 지불한다

**인코딩 전환 조건**

- `hash-max-listpack-entries`: 해시가 `listpack`으로 남을 수 있는 최대 필드 개수
    - Valkey 기본값 512
    - 참고로 Redis 의 기본값은 128 이다
- `hash-max-listpack-value`: 값 하나가 가질 수 있는 최대 바이트 수
    - 기본값 64
    - 값이 단 하나라도 64바이트를 넘으면 해시 전체가 `hashtable`로 바뀐다
- `zset-max-listpack-entries` / `zset-max-listpack-value`: Sorted Set 용, 기본값 128 / 64
- `set-max-listpack-entries` / `set-max-intset-entries` : Set 용, 기본값 128 / 512
- `list-max-listpack-size` : List 용

**인코딩 전환은 단방향**

- 실무에서 중요한 성질이며 필드가 513개가 되는 순간 `hashtable`로 변경되며 다시 100개로 줄여도 `listpack`으로 돌아오지 않는다
- 즉 한순간의 피크가 그 키의 메모리 프로파일을 영구적으로 바꾼다
    - 예시) 장바구니에 봇이 수천 개를 담았다가 전부 비워도, 그 키는 계속 `hashtable`로 남아 메모리를 더 사용한다

**Hash 필드 TTL을 걸면 강제로 전환**

- Valkey 9.0 부터 해시의 필드 하나하나에 TTL을 걸 수 있게 되었다 (`HEXPIRE`, `HSETEX`, `HTTL` 등)
- 그런데 필드 TTL 을 하나라도 걸면 `hash-max-listpack-entries`(512) 와 무관하게 즉시 `hashtable` 로 강제 전환된다
- 값이 하나뿐인데 TTL이 필요하면 Hash 가 아니라 String + EXPIRE 를 써야 한다
    - 항목 하나당 해시 하나 패턴에서 메모리가 약 3배가 된다, String + EXPIRE = 약 86 bytes/key
- 필드 TTL은 한 해시 안에 수명이 서로 다른 필드가 여러 개 있을 때만 값어치가 있다
- 참고로 공식 문서의 내용은 아니며 실제 적용 전 OBJECT ENCODING 으로 직접 확인하는 것이 안전하다

</br>

## String 의 세가지 인코딩

- int : 64비트 정수로 표현 가능한 문자열. 값을 포인터 자리에 직접 저장해서 별도 메모리 할당이 없다
- embstr : 44바이트 이하 문자열. 객체 헤더와 문자열을 같은 메모리 덩어리에 한 번에 할당한다
- raw : 44바이트 초과. 객체 헤더와 문자열을 따로 두 번 할당한다

> 왜 하필 44 바이트일까?
>
> - Valkey 내부에서 모든 값은 robj 라는 객체 헤더로 감싸진다 (타입, 인코딩, 참조 카운트 등을 담는 구조체, 16바이트)
> - 문자열 본문은 sds 라는 자체 문자열 구조로 저장된다 (길이를 미리 들고 있는 문자열, 짧은 경우 헤더 3바이트)
> - robj(16) + sds 헤더(3) + 문자열 종료 문자(1) + 44 = 64바이트
>     - 캐시 라인은 CPU 가 메모리에서 한 번에 읽어오는 최소 단위를 말한다
> - 즉 44바이트는 한 번의 할당, 한 줄의 캐시 라인에 들어가는 최대 길이다
> - embstr 은 수정이 불가능하다. APPEND 같은 변형 명령을 쓰면 raw로 승격되고, 이것도 되돌아가지 않는다

**String + JSON 과 Hash 중 무엇을 쓸 것인가**

- 객체 하나를 저장하는 방법은 두 가지다
    - String 에 JSON 문자열로 통째로 넣기
    - Hash 에 필드별로 쪼개 넣기
- 흔히 메모리로 비교하지만, 실제로 더 중요한 차이는 동시성이다

**String + JSON 의 문제 - read-modify-write 레이스**

- 필드 하나만 바꾸려 해도 다음 3 단계가 필요하다
    - 전체를 읽는다
    - 파싱해서 필드를 수정한다
    - 전체를 다시 쓴다
- 이 사이에 다른 요청이 같은 키를 수정하면 나중에 쓴 쪽이 앞의 변경을 덮어써서 유실된다 - Lost Update
- 막으려면 WATCH(낙관적 락) 나 Lua 스크립트가 필요해지고, 그만큼 복잡도와 비용이 늘어난다

**Hash 장점**

- HGET 으로 필드 하나만 읽는다 O(1)
- HSET 으로 필드 하나만 쓴다 - 전체를 읽을 필요가 없다
- HINCRBY 로 숫자 필드를 원자적으로 증감한다
    - Valkey 는 명령 실행이 단일 스레드라 명령 하나는 중간에 끼어들 수 없다
- 매 요청 JSON 파싱 비용이 없다

**Hash 한계**

- 평면(flat) 구조만 가능하며 중첩된 객체는 표현할 수 없다
- 중첩이 꼭 필요하면 String + JSON 을 사용하거나 별도 모듈이 필요하다 (Valkey 코어에는 JSON 모듈이 없다)

**키를 많이 만들지 말고 해시로 묶어라**

- 키 하나하나가 dict 엔트리, robj, sds 오버헤드를 각각 지불한다
- 그래서 키 100만 개보다, 해시 1만 개 \* 필드 100개가 훨씬 싸다
- 공식 문서는 암시적 샤딩(pre-sharding)을 권장한다
    - 예시) object:1234 를 키 object:12 + 필드 34 로 쪼갠다
    - 해시 하나당 필드 100개 정도가 CPU 와 메모리의 절충점이라고 설명한다

</br>

## Sorted Set 이중 구조

- Sorted Set 은 커지면서 두 개의 자료구조를 동시에 유지한다
    - `skiplist` (Valkey 9.2 부터 B+ 트리) : 순서, 범위, 랭크 조회 O(log N)
    - `hashtable` : member 로 score 찾기 O(1)
- 왜 둘 다 필요한가
    - `ZSCORE key member` 는 이 멤버의 점수가 뭐냐는 질문이라 순서와 무관하다, 트리만 있으면 O(log N) 인데 해시 테이블을 같이 두면 O(1) 이 된다
    - 반대로 `ZRANGE` (순서 범위 조회) 는 해시 테이블만으로는 불가능하다
    - 즉 메모리를 더 쓰는 대신 두 종류의 접근 패턴 모두에 최적 복잡도를 준다

**skiplist**

- 정렬된 연결 리스트 위에 건너뛰기용 상위 레벨을 확률적으로 얹은 자료구조
- 노드를 넣을 때 동전을 던져 레벨을 정함 (50% 확률로 한 층 더 올라간다)

```text
L3:  1 -------------------------> 9
L2:  1 --------> 5 -------------> 9
L1:  1 -> 3 ---> 5 ---> 7 ------> 9
L0:  1 -> 3 -> 4 -> 5 -> 6 -> 7 -> 9
```

- 기대 복잡도는 O(log N) 으로 균형 이진 트리와 같다
- 그런데 트리 회전(rotation) 같은 균형 맞추기 로직이 없어서 구현이 훨씬 단순하다
- 최하위 레벨이 그냥 정렬된 연결 리스트라 범위 순회가 자연스럽다

**Valkey 9.2 에서 skiplist 가 B+ 트리로 교체**

- B+ 트리는 노드 하나에 여러 키를 연속으로 담는 트리다
- 변경 내용
    - 큰 Sorted Set 의 백엔드를 skiplist 에서 B+ 트리로 교체
    - 항목당 약 24 바이트 메모리 절감
    - 랭크 조회 약 7배 빠름 / 순회 16 ~ 36배 빠름
- 왜 빨라지는가?
    - `skiplist`는 노드마다 레벨 포인터 배열을 들고 있어서 포인터 오버헤드가 크고 메모리가 흩어진다
    - B+ 트리는 노드 하나가 여러 키를 연속으로 담아 캐시 라인을 꽉 채운다

</br>

## 실무별 알고리즘

1. 찜하기 / 북마크
    - Set 으로도 "찜했다" / "안했다" 는 표현을 할 수 있다
    - 그런데 실제 요구사항은 거의 아래처럼 번진다
        - "최신순으로 보여주기" - 정렬 필요
        - "20개씩 페이징" - `ZREVRANGE key 0 19`
        - "이번 달에 찜한 것만" - `ZRANGEBYSCORE`
    - Set은 위 요구사항이 어렵다, 그래서 `score` 에 찜한 시각(epoch)을 넣은 `Sorted Set` 이 좀 더 효율적이다

2. 최근 본 상품

- `List` 방식 : `LPUSH` 로 넣고 `LTRIM key 0 19` 로 최근 20개만 남긴다
    - `List` 내부는 `quicklist` 이며 `listpack` 여러 개를 연결 리스트로 이어 붙인 구조이다
    - `LPUSH` / `LPOP` 은 O(1), `LTRIM` / `LRANGE` / `LREM` 은 O(N) 이다
    - 치명적 약점은 중복 제거가 안 된다는 것이다, 같은 상품을 두 번 보면 두 번 들어간다
- `Sorted Set` 방식 : `ZADD key <now> <productId>` + `ZREMRANGEBYRANK key 0 -21`
    - 같은 member 를 다시 `ZADD` 하면 새로 추가되지 않고 score 만 갱신된다
    - "최근 본"의 의미 (또 보면 맨 앞으로) 와 정확히 맞고, 중복 제거가 공짜이다
- 선택의 기준은 중복 갱신이 의미를 갖는가 이다
    - 최근 본 상품 처럼 같은 걸 또 보면 맨 앞으로 와야 하는가? - Sorted Set
    - 알림함, 작업 로그처럼 순수하게 쌓기만 하는가? - List (List 가 더 싸다)

3. 실시간 랭킹
    - 집계는 `ZINCRBY key 1 <member>` 로 한다 - O(log N)
    - 조회는 `ZREVRANGE key 0 9 WITHSCORE` 처럼 필요한 개수만 가져온다
        - 공식 문서에서는 "백만 요소 집합에서 10개를 가져오면 필요한 10개만 비용을 지불한다"
        - 그래서 `ZRANGE key 0 -1` 로 전부 꺼내는 것은 이 장점을 버리는 것 이다
    - 기간별 랭킹은 보통 세가지 중 하나이다
        - 고정 윈도우 버킷 : `rank:d:2026-10-09`, `rank:w:2026-W41` 처럼 키를 날짜로 나누고 TTL 로 자동으로 제거한다. - 가장 단순하다
        - 롤링 윈도우 : 시간 단위 버킷 24개를 `ZUNIONSTORE` 로 합쳐 최근 24시간을 만든다
        - 시간 감쇠 점수 : 점수 자체를 시간 가중치로 섞는다, 키는 하나지만 주기적 재계산이 필요하다
    - 주의할점
        - `ZUNIONSTORE` 를 읽기 경로에서 직접 돌리면 안된다
            - 복잡도가 O(N) + O(M log N) 이라 큰 Sorted Set 여러 개를 합치면 메인 스레드를 길게 점유한다
            - 백그라운드에서 주기적으로 미리 계산해 결과 키에 저장하고 읽기는 그 키만 보게 해야한다
        - `ZUNIONSTORE` 는 결과를 저장하므로 쓰기 명령이다, read replica 에서 돌릴 수 없다
        - `ZREMRANGEBYRANK`로 상위 N 개만 유지하지 않으면 Sorted Set 이 무한히 자란다
            - 동점 처리 : 점수가 같으면 멤버 이름 사전순으로 정렬된다
                - 선착순을 보장하려면 점수에 타임스탬프를 넣는다
                - 단 score 는 64비트 부동소수점 기준 정수 정밀도이다

4. 카운팅
    - 세는 것도 질문에 따라 쓰는 자료구조가 다르다
        - "총 몇 번 발생했는가?" - `INCR` / `HINCRBY` 정확하고 O(1)
        - "몇 명이 왔는가" (중복제외) - `HyperLogLog`
        - "이 사람이 왔는가?" (개별확인) - `Bitmap`
    - `HyperLogLog`
        - 중복을 제외한 개수(카디널리티)를 근사치로 세는 확률적 자료구조
        - 카디널리티는 집한 안의 서로 다른 원소 개수
        - `PFADD uv:2026-10-09 user:1 user:2` - 원소 추가, 원소당 O(1)
        - `PFCOUNT uv:2026-10-09` - 고유 개수 조회
        - `PFMERGE dst src1 src2` - 여러 개를 합친 집합의 고유 개수용 키 생성
        - 특성
            - 메모리는 `HyperLogLog` 하나당 12KB 고정, 1억개를 넣어도 12KB
        - 주의할 점
            - `PFCOUNT` 는 이름과 달리 기술적으로 쓰기 명령
            - 읽기 명령이라고 생각하고 read replica 로 라우팅하면 운영에서 에러가 발생함
            - `PFCOUNT`에 여러 키를 넘기면 즉석에서 병합이 일어나 O(N) 이 되고 상수도 크다
            - 자주 쓰는 합집합은 `PFMERGE`로 미리 만들어 두는 것이 맞다
    - `Bitmap`
        - 비트 하나로 참/거짓을 저장하는 방식, 별도 타입이 아니라 String 에 비트 연산을 하는 것
            - `SETBIT attend:2026-10-09 <userId> 1` - 해당 위치에 비트를 킴
            - `BITCOUNT attend:2026-01-09` - 켜진 비트 수 = 출석자 수
            - `BITOP AND dst key1 key1` - 두 날짜 모두 출석한 사람 계산
        - 유저 1,000만 명의 하루 출석을 1.25MB로 표현할 수 있다
        - 주의할 점
            - 오프셋이 곧 메모리다
            - `SETBIT key 429496... 1` 한줄이면 그 자리에서 약 512MB 가 할당
            - userId 를 그대로 오프셋으로 쓰면 ID 가 커질수록 메모리가 폭증
            - 그래서 0부터 촘촘하게 증가하는 내부 인덱스로 매핑해서 사용해야 함

</br>

## 정리

- 모든 컬렉션 타입은 2~3개의 인코딩을 가지고, 서버가 조용히 고르며, 전환은 거의 항상 단방향이다
    - 코드로는 안보이므로 `OBJECT ENCODING` 과 `MEMORY USAGE` 로 확인해야 한다
- `listpack` 이 O(N) 인데도 작을 때 빠른 이유는 포인터가 없어 캐시 라인에 통째로 올라오기 때문
- `hash-max-listpack-entries` 기본값은 Valkey 512 / Redis 128 로 다름
- Hash 필드 TTL 은 인코딩을 `hashtable` 로 강제 전환, 값이 하나뿐이면 String + `EXPIRE` 가 효율적
- String + JSON 과 Hash 의 결정적 차이는 메모리가 아닌 `read-modify-write` 레이스
- Sorted Set 은 트리 + 해시 테이블 이중 구조
