# 세션 스토어

- Valkey 를 캐시로 쓰는 사례는 흔하지만, 세션 저장소로 쓰는 것은 성격이 다른 용도이다
- 같은 서버를 쓰더라도 설계 기준을 캐시와 똑같이 잡으면 문제가 생긴다

</br>

## 세션은 캐시가 아니다

- 캐시의 정의는 잃어버려도 원본에서 다시 만들 수 있다는 것이다
    - 그래서 캐시는 비어 있어도 서비스가 느려질 뿐 동작은 한다
- 세션은 그렇지 않다, Valkey 가 원본 데이터이다
    - 세션을 잃으면 되살릴 원본이 없다
    - 그러므로 영속성(RDB/AOF) 특성, 복제 및 페일오버, 읽기 실패 시, 커넥션 타임아웃 등 고려해야할 특성들이 많다

**커넥션 설정을 캐시와 같이 사용하면 안된다**

- 캐시용 커넥션은 보통 아래처럼 잡는다
    - 명령 타임아웃을 아주 짧게 (예: 50ms)
    - 오프라인 큐 비활성화 -> 연결이 끊기면 쌓아두지 않고 바로 실패시킨다
    - 목적은 캐시가 느리면 즉시 포기하고 원본 DB로 간다
- 세션에 같은 설정을 쓰면 포기하는 순간 로그아웃이 된다
- 그래서 같은 Valkey 를 쓰더라도 커넥션 풀을 용도별로 분리하는 것이 맞다

</br>

## 무엇을 저장하는가

- String + 직렬화
    - 세션 객체 전체를 JSON 등으로 직렬화해 String 하나에 넣는다
        - 장점 : 단순하다, 읽기도 쓰기도 한번이다, TTL이 키 하나에 붙으므로 만료 관리가 직관적이다
        - 단점 : 필드 하나만 바꾸려 해도 전체를 읽고 수정해서 다시 써야 한다 (read-modify-write)
            - 그 사이 다른 요청이 같은 세션을 수정하면 나중에 쓴 쪽이 앞의 변경을 덮어써서 유실된다
            - 매 요청 직렬화, 역직렬화 비용이 든다
- Hash
    - 세션의 각 속성을 해시 필드로 나눠 담는다
        - 장점 : `HGET` 으로 필요한 필드만 읽는다, `HSET` 으로 필드 하나만 갱신한다, `HINCRBY` 같은 원자적 연산을 쓸 수 있다
        - 단점 : 중첩 구조를 표현할 수 없다, TTL이 키 단위라 세션 전체 만료에는 맞지만 필드별 수명은 원래 표현이 안된다

**판단 기준**

- 세션을 통째로 읽고 통째로 쓰는 패턴이면 String 이 단순하고 충분하다
- 세션 중 일부만 자주 바뀌거나(장바구니 수량, 최근 활동 시각 등) 동시 수정 가능성이 있으면 Hash 가 맞다

**세션을 Hash 로 쓰면서 필드별 TTL 을 거는 것**

- Valkey 9.0 부터 해시 필드 하나하나에 TTL 을 걸 수 있다 (`HEXPIRE`, `HSETEX`)
- 그런데 필드 TTL 을 하나라도 걸면 해시 인코딩이 `listpack` 에서 `hashtable` 로 강제 전환된다
    - `listpack` 은 작은 컬렉션에 쓰는 압축된 선형 구조, `hashtable` 은 일반 해시 테이블을 말한다
    - 필드 개수 임계값 과 무관하게 전환된다
- 어떤 측정에서는 세션 하나당 해시 하나 같은 패턴에서 메모리가 약 3배가 된다
- 세션 전체에 하나의 만료 시간만 필요하다면 필드 TTL 을 쓸 이유가 없다

</br>

## TTL 갱신에서 두 가지 문제점

**1. `SET` 으로 세션을 갱신하면 TTL 이 사라진다**

- `SET` 은 키를 통째로 교체하는 명령이라 옵션을 주지 않으면 기존 TTL 을 버린다
- `GETSET` 도 같은 이유로 TTL 을 날린다
- 반대로 `APPEND`, `INCR` 처럼 값을 변형하는 명령은 TTL 을 유지한다
- 세션에서 이 문제에 걸리면 만료되지 않는 세션 키가 무한히 쌓인다

```text
SET session:abc "<값>" EX 1800 -> TTL 1800
SET session:abc "<새 값>" -> TTL 이 -1(영구 키) 가 된다
SET session:abc "<새 값>" KEEPTTL -> TTL 유지
```

**2. 활동할 때마다 TTL을 연장하는 로직**

- 흔한 요구사항은 마지막 활동 시점부터 30분이다
- 단순하게 매 요청 `EXPIRE session:abc 1800` 을 호출하면 된다
- 다만 이미 더 긴 TTL 이 걸려 있는 경우 줄이면 안 되는 요구가 있으면 조건부 옵션을 쓴다
- 예전에는 TTL 로 읽고 비교한 뒤 `EXPIRE` 하는 3단계였고 그 사이 경쟁 조건이 있었다

</br>

## 영속성과 복제

- 세션은 원본이므로 RDB / AOF 를 꺼두면 안 된다
    - RDB 는 특정 시점 스냅샷, AOF 는 쓰기 명령을 순차 기록하는 방식을 말한다
    - 재시작이나 장애 복구 시 세션이 남아 있으려면 둘 중 하나는 켜져 있어야 한다
- 복제 (replica) 와 자동 페일오버도 사실상 필수다
    - 노드 하나가 죽었을 때 세션 전체가 날아가면 서비스 전체 로그아웃이다
