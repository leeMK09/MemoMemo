## EXPIRE의 조건부 옵션 (7.0.0)

- `NX` : TTL이 없을 때만 설정
- `XX` : TTL이 있을 때만 갱신
- `GT` : 새 TTL이 기존보다 클 때만
- `LT` : 새 TTL이 기존보다 작을 때만
- `GT`/`LT`는 영구 키를 무한대 TTL로 취급한다 -> 영구 키에 GT는 아무 일도 안 일어나고, LT는 항상 적용된다
- 예시) 세션 연장에서 이미 더 긴 TTL이면 줄이지 마라를 `EXPIRE session:x 1800 GT` 한 줄로 표현한다

## 만료는 어떻게 일어나는가

- TTL이 지났다고 그 순간 키가 지워지는 것은 아니다
- `Passive (lazy) expiration`
    - 클라이언트가 그 키에 접근할 때 TTL을 확인하고 만료됐으면 그때 지운다
    - 장점 : 공짜. 접근 경로에 검사 하나 끼우면 쉽게 적용가능
    - 결합 : 아무도 읽지 않는 만료 키는 영원히 메모리에 남음
- `Active expiration cycle`
    - 서버가 주기적으로 돌며 찾아 지운다
    - `Slow cycle` : 서버 주파수(보통 10Hz), DB당 20개 키 샘플링, 목표는 만료 키를 10% 이하로 유지, 상한 CPU 25%
    - `Fast cycle` : 최대 1000us 실행, 같은 간격으로 반복, 만료 키가 10% 이하로 추정되면 중단
- TTL에 지터를 줘야하는 이유
    - 만료와 축출도 메인 스레드에서 실행된다면 해당 사이클도 메인 스레드에서 실행된다
    - 같은 시각에 만료되는 키가 수십만 개면, active expire cycle이 그걸 지우느라 메인 스레드를 25%까지 점유
    - 그 25%는 명령 실행에서 빼앗아 오는 것

**복제에서의 만료**

- Replica는 키를 스스로 만료시키지 않는다
- Primary가 보내는 DEL을 기다린다
- Primary가 키를 만료시키면 DEL을 합성해 AOF에 기록하고 모든 replica에 전파
- Replica는 그 DEL을 받기 전까지 메모리에서 지우지 않음
- 다만 읽기 요청에는 논리적으로 만료 처리해서 값을 반환하지 않음
- Replica가 primary로 승격되면 그때부터 독립적으로 TTL을 관리
- 이렇게 설계한 이유
    - Replica가 독립 판단하면 시계/오차/타이밍 차이로 Primary로 상태가 갈라짐, 만료를 Primary만 내리는 결정으로 만들고 결과(DEL)을 전파하면 상태가 항상 수렴됨
- 참고: read replica의 DBSIZE가 primary 보다 클 수 있다

**maxmemory와 축출 정책**

- `noeviction` : 한계 도달 시 새 쓰기 거부(에러), 읽기는 가능
- `allkeys-lru` / `-lfu` / `-random` : 전체 키 대상
- `volatile-lru` / `-lfu` / `-random` : TTL이 걸린 키 중에서만
- `volatile-ttl` : TTL 키 중 남은 TTL이 가장 짧은 것 부터
- LRU : 정확한 LRU는 모든 키를 접근 순서 연결 리스트로 관리해야 하고 그 포인터가 키당 메모리를 먹는다
    - 그래서 샘플링 근사를 사용한다 `maxmemory-sample 5(기본)`로 무작위 5개를 뽑아 그중 가장 오래된 걸 축출
    - 공식 문서는 샘플 10이면 정확한 LRU에 매우 근접한다고 설명한다
- LFU :
    - `lfu-log-factor 10` -> 카운트 포화 속도
    - `lfu-decay-time 1` -> 몇 분마다 카운터 감쇠, 0이면 감쇠 없음
    - 감쇠가 없으면 한때 인기였던 키가 영원히 살아남게 된다

## 객체 캐싱과 Hash 필드 TTL (Valkey 9.0)

- TTL : String + JSON 방식이며 부분 조회가 아닌 전체를 읽고 파싱
- Hash : 예전엔 키 단위만 처리하는 방식이며 부분 조회를 시도 (`HGET user:1name`)
- Hash의 오랜 약점이 필드마다 다른 수명을 줄 수 없다 였다
- 기능 플래그를 해시 하나에 모으는데 어떤 건 수 분짜리 실행, 어떤 건 수 주짜리 롤아웃이면 타엽된 TTL을 사용하거나 별도 키로 쪼개 키 개수를 폭증시키는 방식으로 해결했다
- 이 문제를 Valkey 9.0에서 해결했다
- 선택한 방식은 `vset(volatile set) + 코스 버킷 + 적응형 인코딩` 방식이다
    - 필드의 만료 타임스탬프를 시간 버킷에 매핑하고, 버킷이 커지면 더 작은 윈도로 쪼개서 버킷 안 항목수에 따라 인코딩을 바꾼다
- 정확한 시간 대신 버킷(근사)를 사용해서 메모리와 스캔 비용을 아낀다
